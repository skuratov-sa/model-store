# Ответы бэкенда для фронтенда

Актуально для Java-бэкенда в `master` на 15.10.2026. Ниже — ответы на B1–B4 и N1–N2 из `backend_questions.md`. Статусы и коды ошибок в примерах указаны так, как их возвращает API.

## B1. Когда можно открыть обращение по заказу

Покупатель и продавец могут открыть `DISPUTE` или `CANCELLATION_REQUEST` только по своему заказу. Одновременно у заказа может быть не более одного обращения в состоянии `OPEN`. Для обоих запросов обязателен непустой `comment`.

| Действие | Условия | Запрос | Что меняется |
| --- | --- | --- | --- |
| Запросить отмену | `AWAITING_PREPAYMENT` и `paymentProofImageId == null`; либо `AWAITING_PAYMENT`, `paymentProofImageId == null` и `prepaymentAmount` равна `null` или `0` | `POST /order/{orderId}/cancellation-request?comment=...` | Создаётся `CANCELLATION_REQUEST/OPEN`. Статус заказа не меняется. |
| Открыть спор | Статус `AWAITING_PREPAYMENT_APPROVAL`, `AWAITING_PAYMENT`, `ASSEMBLING` или `ON_THE_WAY` **и** `paymentProofImageId != null` | `POST /order/orders/{orderId}/DISPUTED?comment=...&imageIds=...` | Создаётся `DISPUTE/OPEN`, заказ переходит в `DISPUTED`. |
| Сообщить об оплате после отмены | Только покупатель; заказ в `CANCELLED`; ранее для этого заказа не создавали `PAYMENT_APPEAL`; нет другого открытого обращения | `POST /order/{orderId}/payment-appeal?comment=...&imageIds=...` | Создаётся `PAYMENT_APPEAL/OPEN`, заказ переходит в `DISPUTED`. |

`imageIds` для спора и обращения об оплате после отмены необязательны. Если доказательства добавляются, изображения сначала загружаются как изображения заказа (`tag=ORDER`, `entityId={orderId}`), затем их ID передаются в `imageIds`. Запрос отмены `imageIds` не принимает.

Прямая отмена — отдельное действие: `POST /order/{orderId}/CANCELLED` с JSON `{"comment":"Причина"}`. Она доступна покупателю или продавцу **только из `BOOKED`** и переводит заказ в `CANCELLED`. Покупатель может так отменить и заказ, созданный у продавца-бота. Сам бот через пользовательский endpoint своими заказами не управляет: для него действует административный маршрут из B4. Поле `closureReason` в DTO существует, но текущая реализация использует `comment`.

После любого действия перечитывайте заказ и `GET /order/{orderId}/cases`. Открытый запрос отмены нельзя определить по одному `actualStatus`: при его создании статус заказа остаётся прежним.

## B2. Где взять подтверждение оплаты до первого обращения

В каждом `FindOrderResponse` есть поле `paymentProofImageId: number | null`. Оно заполняется из `imagePaymentProofId` заказа и доступно в списках:

- `GET /order/customer`;
- `GET /order/seller`;
- `GET /admin/actions/agent-orders` и `GET /admin/actions/agents/{agentId}/orders`.

`null` означает, что у заказа пока нет зарегистрированного подтверждения оплаты в самом заказе. Для доступности первого спора проверяйте **и статус из B1, и это поле**. На этапе `AWAITING_PAYMENT` поле может указывать на чек предоплаты; оно само по себе не означает, что покупатель подтвердил полную оплату. После `PAYMENT_APPEAL` доказательства могут находиться в `caseImages`, даже если это поле остаётся `null`. Массив `images` показывает изображения заказа без указания их назначения и не заменяет `paymentProofImageId`.

Признака открытого обращения в `FindOrderResponse` нет. Для точного состояния обращений нужен `GET /order/{orderId}/cases`; у нового заказа он может вернуть пустой массив.

## B3. Создание товара-розыгрыша

Новый `GIVEAWAY` создаётся администратором через `POST /products` с `availability: "GIVEAWAY"` и вложенным объектом `giveaway`. Обычному пользователю этот тип недоступен (`403 ACCESS_DENIED`). Для администратора не требуются предварительно созданные способ получения оплаты и социальная сеть продавца.

Пример запроса:

```json
{
  "availability": "GIVEAWAY",
  "name": "Приз розыгрыша",
  "description": "Описание приза",
  "giveaway": {
    "enabled": true,
    "telegramUrl": "https://t.me/example_giveaway",
    "startAt": "2027-06-01T12:00:00Z",
    "endAt": "2027-06-07T12:00:00Z",
    "winnersCount": 1,
    "rules": "Условия участия",
    "homeText": "Текст для главной страницы"
  }
}
```

Правила полей при создании:

| Поле | Правило |
| --- | --- |
| `price` | Можно опустить: сервер установит `0`. Положительная цена для `GIVEAWAY` не требуется. |
| `currency` | Можно опустить: сервер установит `RUB`. |
| `count` | Можно опустить; для розыгрыша сервер всё равно сохранит `null`. Если передать `0` или отрицательное число, запрос отклоняется ещё до обнуления. |
| `prepaymentAmount` | Не передавайте: для розыгрыша сервер сохраняет `null`. Переданное значение сначала проходит общую проверку предоплаты. |
| `categoryIds`, `imageIds` | Необязательны; можно опустить или передать пустые массивы. |
| `externalUrl` | Не требуется для `GIVEAWAY`. |
| `name`, `description` | На уровне хранения допускают `null`, но для видимой карточки их следует заполнить. |
| `giveaway.enabled` | Можно опустить: при создании по умолчанию `true`. При `true` дата окончания должна быть в будущем. |
| `giveaway.telegramUrl` | Обязательная HTTPS-ссылка на `t.me` или `telegram.me` с непустым путём. |
| `giveaway.startAt`, `giveaway.endAt` | Обязательны; передавайте ISO 8601 с часовым поясом, `startAt < endAt`. |
| `giveaway.winnersCount` | Обязательное положительное целое число. |
| `giveaway.rules`, `giveaway.homeText` | Обязательные непустые строки. |

Периоды двух **включённых** розыгрышей не должны пересекаться. Запланированный розыгрыш имеет статус `AWAITING_GIVEAWAY`, начавшийся — `ACTIVE`. При `enabled=false` розыгрыш скрыт из публичной выдачи; его настройки по-прежнему должны быть корректны.

## B4. Административная отмена заказа продавца-бота

Администратор вызывает `POST /admin/actions/agents/{agentId}/orders/{orderId}/CANCEL?comment=...`. Сервис проверяет, что заказ принадлежит указанному боту, и использует тот же переход, что и прямая отмена: **только `BOOKED -> CANCELLED`**. Из остальных статусов `CANCEL` недоступен. При успехе действие записывается в историю административных действий.

Это не ограничивает покупателя: покупатель заказа продавца-бота может самостоятельно выполнить `POST /order/{orderId}/CANCELLED`, пока заказ в `BOOKED`.

## N1. HTTP-статусы и машинные коды ошибок

Ошибки приходят в общем формате `{ "code": "...", "message": "...", "status": 400, "timestamp": "...", "details": null }`. Для логики интерфейса используйте `code`; текст `message` можно показать пользователю.

| HTTP | `code` | Ситуация |
| --- | --- | --- |
| 409 | `ORDER_CASE_ALREADY_OPEN` | У заказа уже есть обращение `OPEN`; относится к спору, запросу отмены и обращению об оплате. |
| 409 | `PAYMENT_APPEAL_ALREADY_EXISTS` | Для заказа уже создавали `PAYMENT_APPEAL`, даже если оно завершено. |
| 409 | `ORDER_CASE_ALREADY_RESOLVED` | Администратор повторно решает завершённое обращение или меняет его Telegram-ссылку после завершения. В том числе при одновременных решениях второй запрос получает этот код. |
| 400 | `ORDER_CASE_INVALID_TRANSITION` | Статус заказа, наличие чека или текущее состояние не позволяют выполнить действие; также возможен конфликт версии обращения. |
| 400 | `ORDER_CASE_INVALID_OUTCOME` | Выбран исход, недопустимый для данного типа обращения или исходного статуса. `LEGACY` нельзя передавать для нового решения. |
| 400 | `GIVEAWAY_WINDOW_OVERLAP` | Период включённого розыгрыша пересекается с другим включённым розыгрышем. |

Пустой `comment` возвращается как `400 BAD_REQUEST`; часть других общих ошибок валидации — как `400 INVALID_REQUEST`. При `ORDER_CASE_ALREADY_OPEN` обновите заказ и `/cases`: другой запрос мог создать обращение раньше. При `GIVEAWAY_WINDOW_OVERLAP` подсветите даты розыгрыша.

Допустимые исходы для административного `POST /admin/actions/order-cases/{caseId}/resolve?outcome=...&comment=...`:

| Тип обращения | `outcome` | Результат для заказа |
| --- | --- | --- |
| `CANCELLATION_REQUEST` | `CANCELLED` или `REJECTED` | Отмена заказа либо сохранение текущего статуса. |
| `DISPUTE` | `BUYER`; `SELLER` только если спор открыт из `ON_THE_WAY` | `FAILED` либо `COMPLETED`. |
| `PAYMENT_APPEAL` | `BUYER` или `SELLER` | В обоих случаях заказ возвращается в `CANCELLED`; исход фиксирует решение по обращению. |

## N2. Валюта в деталях обращения

`OrderCaseDetail` содержит `currency` — валюту товара, сохранённую **на момент оформления заказа** (`productCurrency`). Поле есть и в пользовательском `GET /order/{orderId}/cases`, и в административном `GET /admin/actions/order-cases/{caseId}`. Оно относится к суммам `totalPrice` и `prepaymentAmount` даже если валюта товара позже изменилась. Значение передаётся строкой из enum `Currency`, например `RUB` или `USD`.
