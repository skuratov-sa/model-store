# Order creation (migration 24)

Initial base: local `master` at `e6fe7445c89fdbb83c06ac21331e95fbf9aad2c2`. The audit fast-forwarded this branch to local `master` at `cd52fa6b9094bfefa92a7dc06a0b7c5f34204416`, retaining all task-24 files. Accepted dependencies: 16, 16.1, 06, 07, 09, 12, 18; the newer base also contains 04.4.
Scope: `modern/ordering/create/**` and tests for this package. Legacy Java/reactive code, shared HTTP/security, schema, other contexts, and `MIGRATION_PLAN.md` are outside this change.

The booking transaction locks all involved participant rows in ascending ID order before catalog reservation locks product rows in ascending ID order. The seller IDs come from a scalar preliminary read; product ownership is checked again against the locked catalog snapshots. This aligns booking with basket mutation's participant-first order, including the product FK lock on basket insertion. All order inserts, the database history trigger, reservation, and owner-side basket removal share one JPA transaction.

## Stage 1 result (17 October 2026)

- `GET /order` and `POST /order/BOOKED` run in the `modern` profile. Both use the verified `Actor`; booking accepts signed `access` tokens for `USER` and `ADMIN` and rejects `agent_access`. The route therefore does not invoke `VerifyAgentAccess`. `GET` retains the legacy preparation behavior for visible own and agent products; booking rejects both.
- The application merges duplicate product IDs with checked addition and first-line delivery fields. It reserves the sorted batch through `ProductReservation`, validates owner, seller, address and transfer against database state, inserts immutable product/price/currency/availability snapshots, then removes booked basket items through `BasketUseCases.remove`. The existing `AFTER INSERT` trigger creates BOOKED history. A late insert failure rolls back earlier orders, history, basket removal and stock in the same JPA transaction.
- The only direct write in this package is `INSERT INTO "order"`. Participant, product, address and transfer queries are scalar reads or row locks. Product stock writes stay in the catalog reservation port; basket deletion stays in its owner use case. A signed access token for a `BLOCKED` or `DELETED` buyer keeps legacy booking access; the shared token verifier still enforces signature, token type and claims.
- Legacy HTTP was measured on isolated embedded PostgreSQL: preparation and BOOKED response shapes, visible own/agent preparation, exact own-product code/message, signed `BLOCKED`/`DELETED` buyer booking, and agent-seller booking. Agent-seller booking succeeds in legacy but is rejected in modern as explicitly required by item 24. Record this intentional difference for migration item 32.
- Verification after the audit: 12 modern integration tests and 4 legacy HTTP tests, all passed with no errors; `bootJar` passed after the tests. Tests use embedded PostgreSQL, real test RSA keys and mocked SMTP/S3. They cover multi-line booking, duplicate/negative/overflow quantities, PREORDER, limited/unlimited stock and snapshots, authorization, whole-batch rollback including a failure after the first insert, and concurrent order/order (including reciprocal buyers), order/basket add/update, order/product update, order/address delete and order/transfer delete.

## Independent audit findings

- Legacy `TransferServiceImpl.findByParticipantId` includes only `ACTIVE` methods and emits `404 TRANSFER_NOT_FOUND` when none exist. The earlier stage incorrectly returned an empty list and accepted a deleted method. Preparation and booking now distinguish no active method (`404`) from a wrong/deleted selection when other active methods exist (`400 INVALID_TRANSFER`). Booking locks active transfer rows, so a concurrent status change cannot invalidate the selected method before commit. A buyer with no address receives `addresses: []` when the seller has an active method, as measured through legacy HTTP.
- Address validation accepts a deleted address only when the buyer's link still exists, as the legacy order service does. It locks the address row before the participant-address link, matching the modern owner delete order and preventing link removal between validation and insert. Address IDs are locked in ascending order. Seller IDs are preliminarily read, participant locks are acquired in ascending order, and the catalog snapshot is checked after product locks; an ownership mismatch aborts the whole transaction.
- Domain code has no Spring, HTTP, JPA, or foreign context entity imports. `BookingDraft` calculates prepayment and total from the locked catalog scalars; JDBC only persists those scalars. Typed domain problems map to legacy HTTP status/code/message in the API layer. The `AFTER INSERT` trigger writes initial history once; ordering adds no duplicate history write. All owner writes outside `"order"` remain delegated to catalog and basket ports.
- Real RSA HTTP tests cover guest, `USER`, `ADMIN`, refresh and `agent_access`; the latter is explicitly rejected by this route, so `VerifyAgentAccess` is not applicable. Legacy allows an agent-owned product to be BOOKED, whereas task 24 explicitly forbids it in modern. This is the one intentional policy difference recorded for item 32. Booking a product owned by the customer returns the legacy `400 OWN_PRODUCT_ORDER_FORBIDDEN` message. `GET /order` still prepares visible own and agent products, matching legacy.
