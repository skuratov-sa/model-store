# Image command (migration 12)

`POST /images?tag=...&entityId=...` accepts multipart parts named `files` and returns a JSON array of IDs. `DELETE /images?ids=...&tag=...` marks active rows `DELETE`; the existing cleanup scheduler removes their S3 variants later. Both routes run only in the `modern` servlet profile and use the shared authenticated `Actor`.

The upload checks ownership, then decodes and encodes one file at a time and writes its original, medium, and thumbnail JPEGs. It uses the three legacy S3 key paths (`original/<name>`, `medium/<name>`, `thumbnail/<name>`) under the existing tag bucket. New basenames use a full random UUID and `.jpg` to make accidental overwrite of an existing object negligible. After all files are stored, one PostgreSQL transaction checks ownership again and inserts all image rows. The DB transaction contains no S3 calls. Participant images start `ACTIVE` and are bound to the uploading participant even when `entityId` is omitted; other images start `TEMPORARY`. Rows retain the existing `filename`, `tag`, `status`, `entity_id`, `uploaded_by`, `content_type`, `width`, and `height` columns.

If initial authorization fails, nothing has been written. If encoding a later file, an S3 write, or the DB transaction fails, every attempted S3 key is deleted, including the key whose PUT failed, because that PUT might have reached S3. Each delete is retried up to three times. A failed DB transaction rolls back the entire batch. If S3 itself refuses cleanup after these retries, the response is a server error and the remaining bucket/key pairs are logged. That case cannot be made atomic with the current PostgreSQL and S3 interfaces; the logged keys require operational reconciliation. A process crash between S3 writes and compensation has the same limitation. No new table or background worker is introduced by this migration.

The ownership rules mirror the old image service for product owners, administrators of agent products, order parties, and participant images. An unassigned `entityId` remains valid for staged PRODUCT and ORDER uploads. System uploads are restricted to administrators. An authenticated, active participant is required. Delete verifies every requested row in one transaction and rejects an unauthorized, missing, or repeated ID without changing any row. `ORDER` and `SYSTEM` images cannot be deleted through this route.

Profile photo integration is already present in `modern/identity/participant`: `UpdateParticipant` invokes `ParticipantImagePort.replace` in its DB transaction, accepting an `ACTIVE` image whose `entity_id` is null or matches the current participant and marking old active photos `DELETE`. That port does not check `uploaded_by`. To prevent a second participant from claiming a new unassigned photo by guessing its ID, this command always stores its uploader's ID as `entity_id` for PARTICIPANT uploads. The profile update still accepts the returned image ID. Existing unassigned participant rows created by the legacy path retain the port's older claim behavior until that separate package is changed. Product and order command migrations must claim their `TEMPORARY` uploads using `uploaded_by` and their own entity access rules.

The servlet multipart request limit is 10 MiB from the existing application configuration. This command also limits a single request to 10 MiB, uses the configured participant/product image counts, rejects undecodable files and images over 16 million pixels, and always emits JPEG variants. Client filenames are never used as object keys or echoed in validation errors. These validation limits, the participant binding, and the admin-only system upload are stricter than the old reactive implementation.
