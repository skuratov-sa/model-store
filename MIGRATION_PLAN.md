# Переход model-store на Kotlin, Spring Boot 4 и JPA

## Цель и неизменяемые условия

- Новая реализация пишется в **этом же Gradle-модуле** под `src/main/kotlin/com/model_store/modern`. В ней используются Kotlin, Spring MVC, синхронный JPA/JDBC и подход DDD. Reactor, WebFlux и R2DBC остаются только в старой реализации и в изолированных переходных адаптерах.
- Старые Java-классы, WebFlux/R2DBC, зависимости и рабочие сценарии **не удалять**. Допускаются минимальные правки Java и замена несовместимой библиотеки, когда это необходимо для совместимости со Spring Boot 4 и сохранения запуска старого режима. Решение об удалении возможно лишь после полной миграции и отдельного согласования.
- Прежние HTTP-маршруты, методы, параметры, JSON, коды ошибок, авторизация и данные PostgreSQL остаются совместимыми. Новая реализация не переписывает существующие миграции Flyway. JPA-модель подстраивается под действующую схему; `ddl-auto=validate` в рабочем режиме.
- Старый WebFlux-вариант должен запускаться и после полного перехода как путь отката. Режим приложения выбирается при старте; по умолчанию — `legacy`. Новый `modern` использует Spring MVC. Неполный `modern` не объявлять готовым к обслуживанию всего API.
- Один чат выполняет **ровно одну отмеченную ниже задачу**. Для каждого следующего пункта координатор создаёт новый чат с отдельной веткой и рабочим деревом от актуальной общей базы. Физическое разделение на Gradle-модули отложено до стабилизации границ предметных областей и оформляется отдельным решением.

## Что выяснено при проверке проекта

- Сейчас это один модуль на Java 21, Spring Boot 3.4.5 и Gradle 8.11.1. Есть WebFlux, R2DBC, Flyway, PostgreSQL, S3, JWT и 33 Java-теста. `ProductServiceImpl` и `OrderServiceImpl` объединяют несколько бизнес-сценариев.
- Категории, товары, пользователи, изображения, заказы, обращения, розыгрыши и кабинет продавца используют общие таблицы и сервисы. В частности, `AdminController` содержит методы сразу нескольких областей. Параллельные чаты не должны редактировать этот контроллер одновременно.
- Некоторые зависимости идут через **конкретные классы** (`EmailServiceImpl` → `ParticipantServiceImpl`, `AdminController` → `OrderCaseService`, `AdminAgentController` → `AdminAgentService`). Подмена интерфейса через `@Primary` их не переключит. Даже там, где она работает, её влияние на все внутренние вызовы нужно отдельно проверить.
- `ImageController` принимает WebFlux `FilePart`; его нельзя просто отсканировать как MVC-контроллер. Одновременное подключение MVC и WebFlux без явного типа приложения выбирает MVC; старый режим должен явно выбирать reactive. При наличии R2DBC автоматическое создание JDBC `DataSource` требует отдельной настройки. Нужны отдельные менеджеры JPA- и R2DBC-транзакций.
- Новые JPA-сущности нельзя использовать как HTTP DTO или как общие объекты всех областей. Существующие PostgreSQL enum, запросы с массивами, блокировки и триггеры требуют точного сопоставления до переноса записи. Таблица справочника без первичного ключа подходит для JDBC-чтения, а не для искусственной JPA-сущности.
- На 03.10.2026 целевые версии: Spring **Boot** 4.1.1 (это не версия Spring Framework), Gradle **9.7.0** и Kotlin Gradle Plugin 2.4.20. Эта пара Gradle/Kotlin входит в опубликованный диапазон полной совместимости Kotlin Gradle Plugin. Совместимость всего проекта и остальных плагинов всё равно подтверждается сборкой в задаче 01.

## Архитектурные правила для каждой Kotlin-задачи

Структура: `modern/<context>/{domain,application,infrastructure,api}`. Контексты: `catalog`, `identity`, `seller`, `media`, `ordering`, `reputation`; внутри `catalog` можно выделять пакеты категорий, товаров и розыгрышей. Новое название вводить только при ясной границе владения данными.

- `domain`: сущности и value objects, инварианты, переходы состояний, доменные ошибки. Без Spring, JPA, HTTP, Reactor и знаний о соседних контекстах.
- `application`: один use case на действие/запрос или небольшую связную группу, порты для хранилища и внешних систем, управление транзакцией на границе команды. Не передавать JPA-сущности наружу.
- `infrastructure`: JPA-сущности и репозитории, SQL/JDBC для сложных запросов, S3/email, реализация портов и явные конвертеры PostgreSQL enum. Для сложного поиска допустим SQL read model, если JPA ухудшает ясность или производительность.
- `api`: MVC-контроллеры, входные/выходные DTO, валидация и преобразование ошибок. Сохранять действующий HTTP-контракт. Доступ к текущему пользователю — через согласованный в задаче 01 `Actor`/security-контракт, а не ручной разбор JWT в каждом контроллере.
- Связи между контекстами: через ID и явные порты. Сущности разных контекстов не связывать JPA-ассоциациями. Один контекст владеет записью своей таблицы; другим доступны согласованные чтения. Не создавать общий «универсальный сервис» и не переносить логику старого большого сервиса целиком.
- Обязательные для каждой задачи критерии: прежний сценарий описан по существующему коду; новая реализация повторяет поведение и ошибки; проверены авторизация, транзакции и граничные случаи; сборка проходит в обоих режимах; старый режим остаётся запускаемым. Подтверждение отдельной задачи не означает готовность всего `modern`.

## Работа нескольких чатов без конфликтов

1. **Первой выполняется задача 01.** Она создаёт и проверяет общую платформу. До её завершения предметную реализацию параллельно не начинать. Если 01 не проходит проверку совместимости Gradle/Kotlin или запуска legacy, галочку не ставить.
2. После 01 разные чаты берут задачи из разных дорожек: каталог, пользователи/продавец, изображения. Заказы начинают после готовности названных зависимостей. Задачи внутри одной дорожки выполнять по указанным зависимостям; несколько задач с общим файлом или таблицей последовательно.
3. Каждому чату — своя ветка `codex/<task-id>-<name>` и отдельное рабочее дерево. В начале записать в своём чате номер задачи, зависимости и список файлов. Не работать параллельно в одной ветке/папке. Один чат не берёт соседнюю задачу «заодно».
4. **Один интеграционный чат владеет** `MIGRATION_PLAN.md`, `build.gradle`, `settings.gradle`, Gradle wrapper, конфигурацией запуска/безопасности, Docker-файлами и общими Kotlin-пакетами. После 01 эти файлы меняются отдельной интеграционной задачей, а не предметными чатами. Каждый рабочий чат сообщает результаты; интеграционный чат переносит готовую ветку и ставит `- [x]` только после проверки критериев. Так чекбоксы общего файла не конфликтуют при слиянии.
5. Рабочий чат пишет только в пакет и тесты своей области. Новые Flyway-миграции, если они действительно потребуются, выдаются и применяются по одной интеграционным чатом: два чата не назначают себе следующий номер миграции. Существующую схему сначала пытаться использовать без изменений.
6. Одинаковая БД для параллельных проверок недопустима: каждому чату отдельная тестовая БД/контейнер или изолированная embedded PostgreSQL. Сборку Gradle вести в своём рабочем дереве. Перед слиянием пересобрать ветку на актуальной базе, после слияния проверить оба режима.
7. Переключение сценариев не считать автоматическим свойством `@Primary`. Для каждого сценария отдельно перечислить все входные точки и конкретные зависимости, выбрать безопасную точку маршрутизации и подтвердить, что `legacy`-путь по умолчанию остался прежним. Где без изменения старой логики такой выбор невозможен, пометить сценарий как «реализован в modern, не подключён в legacy» и включать только с полным MVC-режимом. Скрытую подмену старого сервиса не делать.
8. Когда задача готова: сохранить результаты проверки и известные ограничения рядом с её чекбоксом либо в связанном отчёте, передать интеграционному чату. Только после принятия в общую ветку отмечать `- [x]`; незавершённое оставлять `- [ ]`. Следующую готовую задачу получает новый чат, созданный от принятой общей базы.

## Карта зависимостей и порядок

`01 → {02, 04, 10}` — первые независимые дорожки после общей платформы. Затем каталог: `02 → 03 → 14 → 15 → 16`; пользователи: `04 → 04.1 → 05 → 06`, `04 → {07, 08, 09}`; изображения: `10 → 11 → 12`. Заказы: `16 + 06 + 07 + 09 + 12 → 24`. Розыгрыши: `16 → 21 → 22`. Вспомогательные функции, заказы и администрирование имеют дополнительные зависимости ниже. Рекомендация: не более трёх предметных веток одновременно, затем короткое интеграционное слияние.

Здесь «зависит от» означает, что задача может изучаться заранее, но реализацию и галочку нельзя завершить до слияния зависимостей. В задачах новых областей сначала сохранять публичный контракт; подключение и переключение трафика выполняется только в указанных интеграционных задачах.

### Как запускать параллельные чаты

Это **очередь по зависимостям, а не жёсткие календарные этапы**: после освобождения места создаётся новый чат для готовой задачи, все зависимости которой уже приняты в общей ветке. Предел — три чата с реализацией одновременно и один чат-координатор для слияния и этого файла, всего не более четырёх работающих агентов. Координатор не выполняет предметную задачу параллельно со слиянием. При ограниченных ресурсах достаточно двух исполнителей. Для обычной локальной задачи выбирать Sol Medium; для сложной интеграции, безопасности, транзакций и архитектурных решений — Sol High.

| --- | --- | --- |

После 11 и 04 — **12** | 03 запускать только после принятия 02 в общей ветке. 07, 08 и 09 имеют разные пакеты и могут идти параллельно, если свободны исполнители. |
| Когда готовы 03, 04, 11 | **14** поиск товаров; одновременно продолжать свободные задачи identity/seller/media | После 05 — **06**, после 06 — **13**. Для 15 дополнительно нужны 07, 08, 09; для 16 — 12 и 15. |

Перед запуском согласовать порты между контекстами. |

Перед каждым запуском координатор проверяет в общей ветке галочки зависимостей и фактические коммиты, затем назначает **один уникальный номер одному чату**. Готовая работа из отдельного рабочего дерева сначала попадает в общую ветку и проходит нужную проверку; только затем следующий чат начинает зависимую задачу от обновлённой общей ветки. Ветка, созданная от `origin/master`, может не содержать локально принятую 01 или последующие задачи: проверять точный базовый коммит, а не только имя ветки.

Ранее созданные чаты с поручением целой дорожки не используют для новых пунктов. Каждый пункт получает новый чат после принятия зависимостей. Не считать уже созданное рабочее дерево доказательством, что зависимость завершена.

При доступном счётчике контекста координатор и исполнитель запускают настоящее сжатие примерно на 50% заполнения и обязательно при превышении 70%. Если явная команда сжатия недоступна, не выдавать текстовую сводку за сжатие; кратко передать состояние и продолжить в рамках текущего пункта. После реализации координатор просит исполнителя сжать контекст **в его собственном чате** и подтвердить результат либо отсутствие такой возможности. Затем отдельным сообщением поручает перечитать изменённый код: найти уязвимости, нарушения DDD-границ, отклонения от текущего пункта и старого HTTP/DB-контракта, исправить найденное и сообщить результат. После этого исполнитель коммитит и отправляет свою ветку в удалённый репозиторий. Координатор проверяет коммит и принимает его в общую ветку до установки галочки. Для **каждого следующего пункта** координатор сразу создаёт новый чат от актуальной общей базы; зависимую задачу запускает только после принятия её предпосылок.

Шаблон задания новому чату: «Выполни **только пункт NN** из `MIGRATION_PLAN.md`. Проверь, что все его зависимости уже приняты в общей ветке. Используй отдельную ветку и рабочее дерево от её актуального коммита. Меняй только указанные в пункте пакеты и соответствующие тесты; общие файлы, старый Java-код и сам план не редактируй. Сохрани прежний HTTP/DB-контракт и DDD-слои. Закончив реализацию, сообщи проверенные критерии, ограничения и необходимые действия координатора; дождись отдельного задания на сжатие контекста и ревью перед коммитом. Галочку ставит координатор после принятия». Каждому чату нужна своя тестовая БД; ни один исполнитель не направляет проверки на общую или production БД.

Подготовить документированный запуск/откат и только после этого выбрать modern для целевого окружения. **Готово, когда** обе реализации запускаются из одного артефакта на существующей схеме, данные не требуют отката схемы, план и результаты проверок записаны. **Никакого удаления старого кода в этой задаче.**

## Правило чекбоксов и отчёта

У каждой задачи изначально `- [ ]`. Интеграционный чат ставит `- [x]` после принятия результатов и записывает под задачей: ссылку/хеш ветки или коммита, что проверено, что осталось ограничением. При неуспешной проверке галочка остаётся пустой. Если задача оказалась слишком широкой, до начала реализации разделить её на новые номера и зависимости в этом общем файле; два чата не редактируют одну задачу.

## Что пока не входит в миграцию

Удаление Java-кода или реактивного стека, физическое разбиение Gradle-модуля, изменение клиентского API и необратимая миграция схемы. К физическим модулям вернуться после 32: оценить границы и зависимость контекстов по фактическим Kotlin-пакетам, а не по текущим сервисам.
